  Q2: Does it pack in the format the device accepts?

  The format is known and documented, but no packing of the new kernel has been 
  done. The device boots via Rockchip's KRNL/RKBOOT flow:

  - bootimg.cfg: load 0x60408000, ramdisk 0x62000000, pagesize 0x4000, 32 MB

  - The vendor parameter confirms it: KERNEL_IMG: 0x60408000, MACHINE: 3066,

  waveform_addr=0x7ff00000 and initrd=0x62000000 passed on the cmdline.
  - The loader is RK3026Loader(L)_V2.32_otp.bin (RKBOOT V2.32, chip tag A203).

  rkflashtool and extract.py are present to repack into that format. But the
  report's flashing plan deliberately bypasses the vendor packed format: it uses
  mainline U-Boot via Rockchip back-to-BROM, flashing u-boot-rockchip.bin to
  eMMC sector 0x40, then U-Boot loads the kernel. So "packing in the vendor KRNL
  format" is documented and tooled but not exercised, and the intended path
  sidesteps it. The waveform .wbf was the one artifact actually re-packed
  (extracted byte-identical, 58,936 B with the rkf:v1.0.1 4-byte length prefix).

  Q4: Could mainline U-Boot + mainline kernel change the disk layout? MTD for 
  flash — right choice?

  On the disk-layout freedom: yes, mainline gives you a clean break. The vendor
  cmdline carries this layout:

  mtdparts=rk29xxnand:
    0x2000@0x2000(misc)  0x4000@0x4000(kernel)  0x8000@0x8000(boot)
    0x10000@0x10000(recovery)  0x100000@0x20000(backup)
    0xc8000@0x120000(cache)  0x190000@0x1e8000(userdata)
    0x2000@0x378000(kpanic)  0x100000@0x37a000(system)  -@0x47a000(user)

  Because mainline U-Boot + mainline kernel don't depend on the vendor
  parameter/KRNL chain, you're free to redefine partitions however you like
  (GPT, U-Boot env-defined, or DT partitions node). The vendor scheme is
  Rockchip-NAND-flavored (rk29xxnand, sizes in 512-B sectors) and you'd discard
  most of it (recovery/kpanic/backup are Android-isms).

  On MTD specifically: it is not the right choice for this device. Here's the
  catch, and it's a real one:

  - The hardware is 4 GB eMMC (per the board spec and CLAUDE.md), not raw NAND.
  The vendor cmdline says rk29xxnand and uses mtdparts, but that's the Rockchip 
  rknand / rk_ftl proprietary FTL — a block device presenting an eMMC-like
  interface, mislabeled "nand." It is not a real MTD/raw-NAND controller, and
  mainline has no driver for the Rockchip FTL.
  - Therefore in mainline the storage shows up as /dev/mmcblk0 via 
  dw_mmc-rockchip (the dwmmc host, already covered in the DTS), and you
  partition it as an MMC block device with a normal partition table — not MTD.
  Using MTD (mtdparts, nandwrite, JFFS2/UBI) would be wrong: there's no mainline
  raw-NAND path for this SoC, and layering UBI on top of a hidden FTL is doubly
  wrong.

  So for the migration:
  - Right layout: treat eMMC as a block device. GPT or MBR with e.g. a small
  FAT/raw region for U-Boot + a boot partition + an ext4/f2fs rootfs. U-Boot
  goes at the Rockchip-conventional offset (sector 0x40), which is outside any
  partition — that's why the flashing plan writes u-boot-rockchip.bin to sector
  0x40 directly.
  - What you'd need to do: (1) build U-Boot for the board once Kconfig is wired;
  (2) define the new partition table (GPT recommended — U-Boot and the kernel
  agree on it without a cmdline mtdparts); (3) set root=/dev/mmcblk0pN and an
  initramfs/rdinit in the kernel cmdline; (4) ensure dw_mmc-rockchip + the eMMC
  clock-mux bits (the CON11/CON12 cpll/gpll mux in clk-rk3026.c, flagged as
  hardware-unverified) actually bring eMMC up.
  - MTD would only be relevant for the separate SPI-NOR chip that holds the
  waveform + per-unit VCOM (the E Ink Broadsheet panel-data area). That one is a
  genuine raw flash and could be exposed as an MTD spi-nor device if you ever
  want to read VCOM in-system — but the main storage is not MTD.

  Q2 clarify: Does the documented flow allow booting the unmodified vendor 
  userspace?

  Yes, and that's a smart checkpoint. The vendor userspace is Android, rootfs on
  the eMMC system partition (ext3 per the DOOKU dump), init=/init, mounted by
  the kernel from the mtdparts system entry. A mainline kernel can boot it if it
  satisfies what /init expects, but there are two real friction points:

  1. Storage node naming. Android /init and fstab reference partitions by the
  vendor rknand/by-name paths. Mainline exposes eMMC as /dev/mmcblk0pN. So
  unmodified Android userspace won't find its partitions without a cmdline root=
  override or an fstab patch. Bootable to a shell, but Android's init may stall
  mounting /data, /cache.
  2. No display. Until the EBC driver works, you boot blind (UART only).

  So the honest answer: mainline kernel + vendor userspace boots to the point of
  Android init over UART and is a valid "the kernel works" proof, but it's not
  a clean drop-in — expect to override root=. Your staged plan (UART-shell proof
  → minimal buildroot to light up the screen → PMOS) is exactly right and I'd
  order it that way.

  Q4 clarify: If there's no proprietary FTL, isn't the exposed device raw NAND? 
  Won't using it as a regular block device cause avoidable wear? Where does the 
  FTL actually sit?

  This is the crux, and the answer hinges on which silicon this board actually 
  has. There are two possibilities and they have opposite implications:

  - If it's true eMMC (what the board spec says — "4 GB eMMC"): the FTL is
  inside the eMMC package, on a controller die next to the NAND, invisible to
  the host. Linux talks to it as a standard block device over the dwmmc/MMC bus.
  No wear problem — wear levelling is the eMMC chip's job, always has been,
  regardless of OS. The vendor's rk29xxnand/mtdparts labelling is then just
  Rockchip's historical naming carried forward; under the hood it's already
  block storage.
  - If it's raw NAND + Rockchip rknand (what the vendor cmdline string literally
  says): then the FTL is proprietary firmware in the vendor kernel (rk_ftl,
  closed binary). Mainline has no driver for it at all — not the FTL, not even
  raw access to that specific controller. So you couldn't use it as a regular
  block device or as MTD; mainline simply wouldn't see the storage. In that case
  your wear concern is real and moot, because the mainline path would be
  blocked entirely and you'd have to boot+root from SD card instead.

  I cannot tell which from the files alone — the parameter string says
  rk29xxnand but the board spec says eMMC, and Rockchip mislabels both. This is
  the single most important unknown for the whole migration, and it's
  empirically resolvable on a live device in one command: cat /proc/partitions +
  ls /dev/block/ — if you see mmcblk*, it's eMMC (great); if you see
  rknand*/nand* with no mmcblk, it's raw NAND behind the proprietary FTL
  (SD-card boot only). RK3026 e-readers of this era were usually raw NAND, so
  I'd lean pessimistic until confirmed. This is worth checking before investing 
  in the eMMC-rootfs path. I'll flag it as a gating question rather than assume.

  initramfs: do we even need one? Why not build drivers in and disable modules?

  You're right — for this device, skip the initramfs. An initramfs earns its
  place when the kernel must do something complex before it can reach the root
  device (decrypt LUKS, assemble RAID/LVM, probe exotic storage, load
  firmware-dependent drivers). None of that applies here: one fixed eMMC/SD
  controller, no encryption, no RAID. So the clean design is CONFIG_MODULES=n, 
  everything boot-essential built in (=y), root=/dev/mmcblk0pN rootwait and the
  kernel mounts rootfs directly. rootwait covers async MMC probe. This also
  matches the project's low-code/single-image ethos and shrinks the image.
  Modules only matter once PMOS wants hot-pluggable stuff (USB WiFi dongle) —
  and even then you can build the RTL8188EU in. I'll drop the initramfs from the
  plan; built-in drivers + rootwait it is. (If raw-NAND turns out to be the
  case, root moves to SD — same approach, root=/dev/mmcblk0p1 pointing at the
  card.)

  ---
  "ensure dw_mmc-rockchip + the eMMC clock-mux bits actually bring eMMC up" — 
  how, exactly?

  Concretely, three things must line up, in order:

  1. Clock mux correctness. In clk-rk3026.c the eMMC clock is CON(12) mux bit 7,
  div bits[14:8], parents {cpll, gpll} — these were derived from vendor
  clock_data.c without hardware verification (called out as the most likely bug
  in the failure-diagnosis table). If the mux bit or parent is wrong, the card
  clock is wrong and the controller either sees no card or fails CMD timing.
  2. dwmmc node + tuning in DTS. &emmc needs clocks = <&cru HCLK_EMMC>, <&cru 
  SCLK_EMMC>, bus-width = <8>, non-removable, cap-mmc-highspeed, and a sane
  max-frequency (start conservative, e.g. 25 MHz, not HS200 — RK3026 era doesn't
  do HS200).
  3. Power rail. eMMC VCC/VCCQ must come up from the ACT8931 regulators before
  probe.

  How to verify — this is empirical, no way around it:
  - Cheapest first: prove it in U-Boot, where MMC_DW_ROCKCHIP is already in the
  defconfig. At the U-Boot prompt: mmc dev 0; mmc info; mmc read 0x60800000 0 1.
  If U-Boot enumerates the eMMC and reads sector 0, the clock mux + dwmmc
  binding are correct — that validates the same clock path the kernel uses
  before you even boot Linux.
  - Then in Linux: dmesg | grep mmc → expect mmc0: new ... card and a partition
  scan. Failure mode mmc0: Timeout waiting for hardware interrupt or no card =
  clock mux wrong → bisect the CON12 bit against a scope or against U-Boot's
  working value.

  So the answer to "how": validate the clock mux through U-Boot's mmc commands 
  first (fast, no kernel needed), then confirm in Linux dmesg. U-Boot is the
  cheap oracle for the exact thing flagged as unverified.

  ---
  The SPI-NOR / VCOM deep-dive — what it is, why read it

  This is the E Ink panel-data flash, and it matters specifically for display 
  quality, not boot. In depth:

  What the chip is. Separate from main storage, the board has a small dedicated
  SPI NOR flash wired to the EBC's display logic (classic E Ink Broadsheet/AM300
  design). It holds two things, at fixed offsets (from epd_spi_flash.h):
  - The waveform (WFM_ADDR 0x886): the LUT that tells the EPD controller how to 
  drive each pixel through each grey-level transition — sequences of
  +15V/−15V/0V pulses per frame. E Ink can't just "set a pixel to grey 7"; it
  has to push the particles through a choreographed voltage sequence, and that
  choreography is the waveform. We already extracted this byte-identical from
  the kernel array (V110_B638_60_VO0102_BTC.wbf), so it's reusable across units.
  - The panel data (PNL_ADDR 0x30000): per-panel factory calibration — part
  number, FPL lot, and critically the VCOM voltage at +0x10 (a 5-byte ASCII
  string like -2.50).

  What VCOM is and why it's per-unit. VCOM is the common-electrode bias voltage
  for the E Ink film. The optimal value is a physical property of each 
  individual panel — it varies unit-to-unit due to manufacturing tolerance, and
  the factory measures it and burns it into that device's SPI NOR. If you drive
  a panel with the wrong VCOM, you get ghosting, washed-out contrast, uneven 
  greys, and faster panel aging. The TPS65185 PMIC has a programmable VCOM
  register (10-bit, 10mV steps) — the driver's job is to read the calibrated
  string from SPI NOR and program it into the TPS65185 at init.

  Why we'd want to read it / expose it as MTD. Our extracted waveform is
  unit-independent and fine to ship. But VCOM is not — it lives only on each
  device's SPI NOR and is not in any of our dumps (it's a separate physical chip
  we never imaged). So:
  - For a first-light bring-up, we use the board default (−2500 mV from
  tps65185_pdata) — display will work but may look slightly off / ghost a bit.
  - For a correct per-unit display, the mainline driver needs to read that SPI 
  NOR at runtime. Exposing it as a spi-nor MTD device (mtd0, read-only) lets the
  EBC driver (or a userspace helper) read PNL_ADDR+0x10, parse the VCOM string,
  and program the TPS65185. That is the one place MTD is genuinely correct on

  Q1: Why is u-boot-rockchip.bin 8.78 MB?

  It's mostly 0xff fill, not code — and the layout is upstream-standard, though 
  the offset is larger than this small board needs.

  The breakdown (I dissected the binary):
  - 0x000: RK SPL header (RK30 magic at 0x800) + the SPL itself — 1.2 KB.
  - 0x2000 → 0x7f8000: ~8 MB of 0xff padding (binman pads with the flash-erased
  value, which is why it superficially looked like "content").
  - 0x7f8000: U-Boot proper as a FIT image — ~380 KB (u-boot.bin is 425 KB).

  So the actual bootloader is ~380 KB; the 8 MB is empty space. The padding
  offset is CONFIG_SPL_PAD_TO=0x7f8000, which is literally the U-Boot upstream 
  default for ARCH_ROCKCHIP (default 0x7f8000 if ARCH_ROCKCHIP in
  common/spl/Kconfig) — it reserves a generous SPL region so big-SoC SPLs (with
  DDR init + TPL) fit before U-Boot. It's harmless on this board (it just means
  U-Boot lives at byte 0x7f8000 of the SD), but it's oversized for RK3026, whose
  SPL is 1.2 KB.

  This is worth tightening: I can set SPL_PAD_TO to something like 0x8000 (32
  KB, matching the SPL size + headroom) so the image is ~450 KB instead of 8.78
  MB. The only constraint is U-Boot proper must land at a sector boundary clear

  Q2: Why is the EBC driver so incomplete?

  Because it's a bring-up driver someone wrote to get something on screen, and 
  the hard parts of E-Ink were deliberately deferred (the driver's own header
  says so). Specifically what's missing and why it's hard:

  - Waveform LUT walker — the driver loads the .wbf via request_firmware but
  never uses it. Real E-Ink needs per-grey-level, per-temperature pulse
  sequences walked out of that LUT; the bring-up driver just does one hardcoded
  GC16 full-refresh. Writing the walker means re-implementing the vendor's
  epd_lut logic (mode tables, temperature compensation) — a substantial chunk.
  - No TPS65185 power/VCOM sequencing — the EPD PMIC needs a strict power-rail
  sequence and per-panel VCOM programming; the bring-up driver does none of it
  (the EBC_VCOM0..3 registers are defined but never written). And the per-unit
  VCOM value lives on a separate SPI-NOR chip we never dumped (it's not in any
  image), so even a complete driver needs that read at runtime or a default.
  - No partial update / A2 / region windowing — only full-screen refresh.

  In short: registering fb0 and kicking a full refresh is ~400 lines; a good
  E-Ink driver (LUT walker + power sequencing + partial updates) is several
  times that and needs hardware to tune. The current driver is honest
  scaffolding — it proves the controller/IRQ/timing path works, which is the
  right first milestone, but it was never finished because finishing requires
  the panel in hand.

  Q3: Why kernel + U-Boot on NAND? Why not support NAND in SPL and U-Boot?

  To be precise about what I implemented vs. what's possible:

  What I did: rootfs on NAND, boot chain (SPL+U-Boot+kernel) on SD. That split
  exists because mainline's Rockchip SPL has no NAND boot path —
  arch/arm/mach-rockchip/spl-boot-order.c only maps BOOT_DEVICE_MMC1/MMC2/SPI;
  there is no BOOT_DEVICE_NAND. So out of the box, mainline cannot load the SPL
  or U-Boot from NAND on this SoC.

  Why not just add it? It's doable but it's real work with a sharp catch:
  1. U-Boot proper reading NAND is the easy half — CONFIG_ROCKCHIP_NAND +
  CMD_MTD/UBI and U-Boot can read a kernel from NAND. I left it out only to keep
  the verified first-light build minimal; it's a small addition.
  2. SPL booting from NAND is the hard half. The mask BootROM loads the SPL from
  whatever device, but for the SPL→U-Boot stage to come off NAND you'd need to
  write a NAND reader into the SPL and it must reproduce the exact ECC scheme, 
  page layout, and bad-block convention the BootROM expects when it reads the
  SPL itself. Get the ECC/randomizer wrong and the chip either won't boot or you
  mismark blocks. That's the part that needs hardware verification and matches
  the closed boot path — substantially more effort and risk than the SD boot
  chain, for the marginal benefit of freeing the SD slot at boot time.

  So the engineering judgment was: rootfs-on-NAND captures ~99% of the value
  (uses the 4 GB internal store, frees the SD for the user's books) for a 
  fraction of the risk, because the NAND controller is already
  mainline-supported. Full SD-free boot is a follow-on project, not a blocker.
